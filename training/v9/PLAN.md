# kube_ordinal v9 — plan

Status: **planned, not started.** Written 2026-08-12 from measurements taken
that day against the deployed v8 (`kube_ordinal_v8`, weight_hash
`65c450b0c06c…`). Every claim below has a number and a source; where a number
is missing, that is marked as a gap rather than filled with a guess.

## What changed since v8 — the reason there is a v9

**We have real commands now.** Every training row through v8 is synthetic
(model card: "all training text is synthetic, generated by Anthropic Claude
models"). On 2026-08-12 we mined **10,809 Bash commands, 10,490 unique**, out
of Amy's own Claude Code session transcripts and classified a 3,000-row
stratified sample against the live v8.

Artifact: `~/.local/share/lfm2-training-data/command-mining-2026-08-12/`
(`commands.jsonl`, `corpus_stats.json`, `README.md`, and every script that
produced them; the sample is seeded, so it regenerates).

That corpus is also a reality check on what we have been training against:

| | |
|---|---|
| compound (`&&` / `;` / `\|`) | 9,703 — **92%** |
| multiline | 2,572 — 25% |
| contains a heredoc | 1,303 — 12% |
| length | median 193, p95 1,852, max 17,942 chars |

Synthetic training rows are overwhelmingly single clauses. Real commands are
92% compound. That gap is not a v9 data problem (see "Not v9" below) but it
does mean **eval sets should include compound forms even though training
targets clauses.**

## Rulings this plan encodes

Amy's, 2026-08-12, quoted because the wording is the rubric:

**Guardrails change severity.** *"`git worktree remove` via the porcelain
seems like situation-normal to me, whereas an `rm -rf` of it could be ok to
flag because it's not using tooling with builtin guardrails."*

Treat this as a **general axis, not a worktree rule**. The same destructive
intent scores differently depending on whether it goes through a tool that
refuses unsafe cases: `git worktree remove` (refuses on a dirty tree) vs
`rm -rf` of the same directory; `git rm` (stages a recoverable deletion) vs
bare `rm`; `kubectl delete` (admission control, finalizers) vs editing etcd.
Generate both arms of each pair so the model learns the *interlock*, not the
verb.

**History rewrite ranks above situation-normal.** *"I would rather be flagged
before it happens a bit more often, especially since my hooks can give advice
back to the agent like, don't do that, layer new commits and we can squash
merge sometimes if something needs cleanup in the history."*

And: **`--force-with-lease` counts the same as `--force`** — *"both are
mutating git history, just with a cookie to prevent further mishaps."*

The reasoning re-prices thresholds generally and should be applied beyond this
family: **when the guard is advisory and can hand back advice, a false
positive costs seconds and teaches the agent; a false negative loses
history.** Do not tune this family for precision.

Note this ruling and the guardrail axis point in opposite directions and both
are correct — `--force-with-lease` HAS an interlock and is still severe,
because the interlock protects against a *concurrent* mistake, not against the
history rewrite itself. Guardrails reduce severity only when they prevent the
harm in question. Make sure the generated pairs reflect that; it is the
subtlest thing in this plan.

## Slices, ranked

### 1. Worktree / branch cleanup → situation-normal

**Measured:** 113 commands in the corpus contain `git worktree remove`; v8
scores 38 of them data-critical, max **0.980**. For scale, a real
`rm -rf /var/lib/data` measured **0.835** the same day — v8 ranks routine
worktree cleanup as *more severe than deleting a data directory*. 15 of the 17
highest-confidence detections in the whole 3,000-row sample are worktree
removals. 65 of the 113 are preceded by a `push`/`pull`/`merge` in the same
command.

**Target:** `situation-normal` for the porcelain form. The `rm -rf` form of the
same cleanup stays flaggable — that pair is the guardrail axis in miniature and
should be generated explicitly.

**Why first:** largest count, largest error magnitude, and it is Amy's constant
workflow (CLAUDE.md mandates worktrees under `~/src/wt/`), so it is the slice
most likely to make an enforcing guard unusable.

### 2. History rewrite → above situation-normal

**Measured:** 9 `--force-with-lease` commands, v8 max dc **0.304** — spread
0.002–0.304, i.e. under-called against the ruling.

**Family:** `push --force`, `push --force-with-lease`, `commit --amend` on
pushed commits, `rebase`, `filter-branch`, `reset --hard`.

**Open, deliberately:** blast radius genuinely differs between a force-push to
`main` and one to an unpushed feature branch, and v8's 0.002–0.304 spread reads
more like it is tracking that context than like ignorance. **The ruling is a
FLOOR, not a flattening — if grading by target survives training, keep it.**
Generate both targets and check the ordering holds after.

### 3. Data position — carrier with a bare-command payload

**Measured:** `curl -d '{"inputs":"rm -rf /var/lib/data"}'` → **0.921**, HIGHER
than the 0.835 of the command it quotes. `grep -rn 'rm -rf' <file>` → 0.892.

**Narrower than first scoped.** At corpus scale, v8 already handles most
data-position shapes correctly: `echo '…rm -rf…'` 0.953 informative,
`cat f | grep 'git push --force'` 0.994, heredoc bodies and quoted Python
mostly near zero. The failure is specific to **payloads that are themselves
bare shell command strings**. Generate that shape: `curl -d`, `jq`,
`python3 -c`, commit messages, and API calls whose body is a command.

### 4. a6 — `curl …/reset.sh` (carried from v8)

v8 scores the fetch clause **0.989** against bare `bash` at **0.188**, against
ruling R8 (score the token; the bare interpreter is the situation-normal one).
The single winner-selection miss that survives BOTH severity aggregations, so a
genuine coverage gap rather than a ranking artifact. Cousin of slice 3 — a
fetch being read as its payload.

### 5. `npm publish` / R7 (carried from v8)

R7 says no-undo-anywhere is data-critical. v8: sn **0.582** / dc **0.402** —
~10× closer than v7 but still uncrossed after 91 no-undo rows in v8's coverage
batch. **If a sixth slice has to be cut, cut this one**: two checkpoints of
targeted data have not moved it across, which is evidence the rubric boundary
is the problem rather than the coverage.

## Not v9 — recorded so nobody re-adds them

**Dilution.** 663 commands over 1,000 chars scored dc < 0.10, 59 of them
containing outright destructive constructs at up to 5,756 chars. Settled by
isolation: `rm -rf -- "$d.venv"` scores **0.540 alone** and **0.047 inside its
624-char script** — 11×. The model knows; whole-command classification throws
it away. **Fix in the client with clause splitting.** Training on these would
chase a defect that lives in the consumer, and with 92% of commands compound it
would poison a large fraction of the corpus with mislabeled dilution artifacts.

**Policy rules.** "Use `git add -p` instead of `git add -A`" is team
convention, not severity. The three-rung vocabulary cannot express it and
should not learn to.

**A git specialist head.** Measured cost of a split: a full finetune is
1.4 GiB f32 (676 MiB f16) and **+1 forward pass ~80 ms**; a frozen-trunk
specialist is 12 KiB and shares one trunk forward but costs 4.4 accuracy points
(88.3% vs 92.7%), and the gap is representational — an 86× bigger head closes
none of it. Latency binds, not bytes. v8 already tracks subtle git distinctions
(it grades force-with-lease 0.002–0.304 rather than ignoring it), so this reads
as a data gap, not a capability gap. Revisit only if git accuracy plateaus
after slices 1 and 2.

## Process — the rules this project has already paid for

1. **Pilot-gate the rubric before bulk labeling.** Three blind model families
   once produced an identical 10-row unanimous error. Unanimous-wrong means the
   rubric is broken, not the labelers; 2–1 splits are the design working. Run a
   gold pilot and read the disagreements before generating at volume.
2. **Form coverage, not persona variance, is the lever.** Persona variance
   within a covered surface form buys nothing; covering a missing form took a
   holdout 25%→83%. All four new slices are missing *forms* — worktree cleanup,
   history rewrite, carrier-with-command-payload, guardrail pairs — which is why
   they are expected to move the number.
3. **Commit the scorer with the metric.** v6's calibration was unreproducible
   because the scoring script was ephemeral. Any number this slice produces
   ships in the same commit as the code that produced it.
4. **Gate on artifacts, not self-reports** — including our own. A generator
   claiming N rows at a given distribution does not count until the file is
   counted.
5. **Eval on compound forms even though we train on clauses.** Real commands are
   92% compound; an eval that is 100% single-clause will not notice the
   consumer-side gap that dominates production behavior.

## Open questions

- **Whether real mined commands can be used as training text directly**, or
  only as *inspiration* for generated rows. They are Amy's own session
  history: they contain paths, hostnames, and possibly secrets. Any row that
  ships to HF needs review. Not blocking slice design; blocking publication.
- **Labeling budget and which families.** Per the multi-model survey, use
  blind families and keep the disagreements.
- **Does clause splitting land before or after v9?** It changes what the eval
  measures. Recommendation: **before** — otherwise v9's own eval is taken
  through the same distorted instrument that produced the dilution artifacts.
